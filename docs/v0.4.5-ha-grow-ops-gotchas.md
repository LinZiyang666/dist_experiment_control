## A. 仍需手动 → 自动化/修复 backlog（朝零手动运维）

1. **seed 发布是手动的**。grow 后 `cluster seeds publish` 才能让 agents 自动发现新 broker（auto-discovery
   本身是自动的，但发布这一步要人做）。**自动化**：membership 变化（join/retire 提交）后，leader 自动从
   各 broker 的 `broker.yaml` public_host/domain 派生 client-dialable 端点、自动 bump seed_generation
   发布。没这步 → 关老 broker 时 agents 切不过去。

2. **proxy status / 订阅按订阅 host 渲染所有 exit**。N=2 后 `tether proxy status` 把 pc732-homed 的 exit
   也标成 `linziyang.top:1400x`（订阅 host），实际 egress 在 `weiland.top:1400x`（端口监听铁证）。
   **风险**：订阅下发给 Clash 的 server host 若也错，pc732-homed 那几条会连不上。**修**：每个 exit 用它
   自己 home broker 的 public_host 渲染，不用订阅 host。（订阅 host 本身为什么固定到 racknerd 也要查。）
   **附带验证**：rebalance 后 broker 端订阅内容是对的（`curl weiland.top/sub/<token>` 每个出口指向其真实
   home：pc732-homed→weiland.top:1400x、racknerd-homed→linziyang.top:1400x）。**但客户端(Clash Verge)的
   proxy-provider 缓存是旧的 → rehome 的节点超时,要手动在 UI 刷 provider**(mihomo 控制器在 Clash Verge 里
   是命名管道、TCP 关,没法外部程序化刷)。零手动运维点：缩短 provider interval / rebalance 后主动让订阅带
   staleness 信号 / 客户端缩短刷新周期。

3. **首次 standalone→clustered 的 NATS mesh `reconcile nats --all` 渲染不出来**。`BuildMergedConf` 从
   现有 conf 的 `cluster{}` 块 harvest mTLS 证书路径；standalone conf 没这块 → 报
   `live conf has no cluster{} block to harvest routes mTLS from`。只能用
   `reconcile nats --manual --secrets-dir --peer <对方>`（显式给 mTLS）。**修**：auto-reconcile 在 conf
   无 cluster 块时 fallback 到 `secrets-dir` 取 mTLS，让 `--all` 能做首次 grow。

4. **former-N1 节点的 JS store reset 是手动 + 有数据损失**。standalone JS 不迁进 clustered meta，重启
   clustered 会孤儿化旧流；runbook 要 `rm -rf /var/lib/tether/jetstream`（丢 history/audit）。
   **自动化**：grow 时自动检测 + 自动 reset（或自动 `nats stream backup`→reset→`restore` 保数据）。
   本次用 `mv jetstream → jetstream.grow-bak.<ts>`（可回滚）代替 rm。

5. **`cluster init` 没有机器可逃生的 confirm**。`confirmTypedNodeID(..., allowMachineEscape=false)` 强制
   TTY 输入 node_id；自动化要 Python pty 喂。（`resnapshot` 有 `--confirm-node-id`+env 逃生，init 没有。）
   **修**：给 init 加同样的 machine-escape confirm（或 `--yes-i-understand` 之类）。

6. **`tether.lock` 被 root `cluster init` 建成 root-owned** → 之后 `sudo -u tether` 跑 offline op
   （resnapshot）开锁 permission denied。**修**：init/install 确保 data_dir + lock 归 broker 用户
   （类似 audit C 的 /etc/tether chown）。本次手动 `chown tether tether.lock` 解锁。

7. **catch-up deadline（opCatchupTimeout=2min）对慢 InstallSnapshot 太短** → join STALLED、要手动
   `cluster ops confirm` 重试（大 DB 经网络装快照 >2min）。**修**：deadline 按快照大小/进度自适应，或
   stall 后自动重试若 joiner 仍在追。

8. **catch-up 探测要 joiner NATS 可达**（`clusterCaughtUp` 经 `SubjClusterCursor` scatter-gather）→ NATS
   mesh 必须先渲染好 joiner 才算追上 → 与"先 join 再 reconcile nats"的 runbook 顺序成鸡生蛋。**自动化**：
   grow 编排里 AddNonvoter 后自动渲染 mesh，再判 catch-up，再 AddVoter。

9. **ctl 没有持久 roster 缓存**（**真机证实 2026-06-28 阶段4**）→ 配的 broker（pc732）一关,本机 ctl 连不上
   `nats: no servers available for connection`、**不会自动切 racknerd**（agents 有 roster_cache 会切）。
   用户预期"cli 理应自己找出路",未达成。**修**：ctl 也持久化发现的 roster（从 cluster seeds）+ 连接失败
   时自动遍历 fallback 端点;或 broker_url 支持多端点列表。**这是用户明确要的功能缺口,优先级高。**

11. **运维命脉/观测通道不能依赖被测死的节点**（**真机证实 2026-06-28 阶段4**）。本机到 racknerd 的 wss
    (`--nats-url linziyang.top:443`)和 SSH 都经 Clash:`linziyang.top` 解析成 fake-ip `198.18.x`、非 Clash
    DIRECT → 走代理链,而链路依赖 pc732 → **杀 pc732 后,我到幸存者 racknerd 的 wss + SSH 同时断**
    (`tls error: EOF` / `Connection closed by 198.18.x`),保护模式期间看不到幸存者(只能靠重启 pc732 后
    事后取证 journal 确认它没崩)。**真 failover 测试前必须先建一条到幸存者的 pc732-独立通道**:SSH key 直连
    racknerd 真实 IP(`23.95.48.156`,需在 Clash 里对该 IP 走 DIRECT 或确认本就 DIRECT)。**零手动运维点**:
    cluster seeds 应让客户端缓存"按真实 IP 直连"的 fallback,使运维/观测不被单点 DNS/代理链卡死。

10. **N=1-clustered JS 陷阱**（已改 actionable 错误但仍要手动）。cluster 模式 + clustered-N=1 conf →
    JS meta 形不成 → broker 退 70 崩溃循环。v0.4.5 报错已指明 remedy，但仍要人手 `reconcile nats
    --to-standalone`。**自动化**：N=1 自动收敛到 standalone（受 R3 "不静默 de-cluster" 约束,需谨慎设计）。
    **附（2026-06-29 在线 force-single 真机证实，见第 12 条）**：这个陷阱在 force-single 后的"被弃节点
    冷重启"上必然触发——pc732 被 force-single 踢出后,它盘上 raft config 仍是 `{pc732,racknerd}`(voters=2),
    冷启动要 clustered JS 2-节点 quorum 而队友已走 → 退 70 起不来。**所以 force-single 后被弃节点不能简单
    重启,只能走 rejoin**(wipe 过时 raft + 作为新 voter 重新 join 幸存者)。

12. **force-single 后客户端名册不自动降级被弃节点 → 设备清单永不收敛到 N=1**（**真机证实 2026-06-29
    在线 force-single 测试**：杀 pc732 整机 → racknerd 在线 force-single 成 N=1,broker 不重启、PID 不变,
    车队无缝 failover 到 racknerd）。**现状（bug）**：force-single 只改 raft 成员配置（→`{racknerd}`）+ 置
    `force_single_active` meta 标记,**完全不碰被弃节点在 `cluster_nodes` 表里的 `phase`**（pc732 仍 `VOTER`,
    只在 status 里标 INCONSISTENT）。而签名名册由 `readRosterBrokers`(`internal/broker/cluster_roster.go:98`)
    **无 WHERE 过滤、全表 SELECT** 连 `phase` 一起发布 → racknerd 仍在每次 register 重签+重推一份把 pc732
    当 `VOTER` 的名册（agent 的 `roster_cache.json` `issued_at` 在 force-single 之后仍列两个 VOTER；cli 的
    `cluster_endpoints.json` 也仍是 floor=weiland.top + seed=linziyang.top）。**后果**：raft 成员（真投票，N=1
    只有 racknerd）与对客户端发布的名册（N=2,pc732+racknerd 都 VOTER）**两个视图脱节**;所有 agent/cli
    failover 列表里那个死的、被踢出的 pc732 端点**永不消失**,每次 failover 还会先去试 `weiland.top`(死 broker)
    再退 racknerd——客户端清单**不会自动收敛到 N=1 现实**。**现状(实测 2026-06-29:此幽灵在线根本删不掉 = pc732 遗留问题)**:`cluster recovery node remove
    pc732 --manual` **被拒**——`RemoveNode` phase-gate(`clusterdrain.go:203`)只放行 RETIRING/
    VOTER_ADD_FAILED/CATCHING_UP,pc732 是 VOTER → 拒;**就算绕过 phase-gate,后面 `RemoveServer(pc732)`
    (`clusterdrain.go:232`)又因 pc732 已不在 raft config(force-single 早移走)报错** → 删 roster 行的
    `PlanClusterNodeRemove` 永远走不到;`cluster retire` 同理(也要 RemoveServer)。**盲区**:force-single 踢出
    节点却留 phase=VOTER,该幽灵**三不沾**——非活 voter(不能 retire)、非转移态(不能 remove)、不在 config
    (RemoveServer 失败)→ **在线无任何删除路径**;唯一现实出路是 rejoin pc732(wipe+回真 N=2,名册自然恢复)。
    **遗留实况**:现网 racknerd N=1 的 roster 卡着一个删不掉的 pc732 幽灵 VOTER(2026-06-29 决定物理关停
    pc732 的 broker+agent、**暂留此幽灵**,待本条修复后再清)。**该怎么修**:force-single 必须区分两类 voter——
    「崩了但仍是成员」(临时宕机,**保留**名册,会回来、quorum 自愈,= 第 9/stage-4 不变量) vs「force-single
    单向踢出」(**应从发布名册降级/排除 + 可在线删除**)。修法(任一/组合):① force-single 把被弃节点 roster
    phase 降级(置成非-VOTER 的 ejected/RETIRING 态,名册自然不再当它 VOTER、且 `node remove` 能收尾);②
    `readRosterBrokers` 按**真实 raft 成员**(不在 raft config 内的不发/标 ejected)过滤,而非裸信
    `cluster_nodes.phase`;③ **`RemoveNode` 放行"不在 raft config 的幽灵"**——先判成员资格,不在 config 就跳过
    `RemoveServer`、直接 `PlanClusterNodeRemove` 删 roster 行(已不在 config,删行不可能 fork quorum,~3 行改动)。
    **优先级高**:N=1 逃生期间所有客户端都背着一个删不掉的死端点,且与第 9 条(ctl 持久 roster fallback)、第 1
    条(seed 自动发布)同属"成员变化后客户端视图自动收敛"这一族缺口。

13. **broker 升级 ≠ `node upgrade`;无 quorum-safe 滚动 broker 升级编排**（**真机证实 2026-06-29 全队升
    0.4.7**）。`node upgrade <nid>` 只对 **agent 进程**做 in-place `syscall.Exec` 重启,**够不到 broker
    systemd 守护进程**;broker 换版本必须 SSH 上去 `install` 新二进制 + `systemctl restart tether-broker`。
    broker 主机上 broker+agent **共用同一份** `/usr/local/bin/tether`(同一个包),二进制**装一次**即可,但
    **两个进程各要重启一次**才加载新版本(我一度还冗余地用 `node upgrade` 把已在盘上的 0.4.7 又下了一遍——
    其实只需重启 agent 进程)。整队升级是手动 4 个 agent(`node upgrade` 各一次)+ 2 个 broker(detached
    `systemd-run` 脚本各一套),零编排。**自动化**:`tether cluster upgrade --all`——一次 install + 重启
    broker 守护 + re-exec 同机 agent,**滚动一台一台、先 transfer-leader 再重启**(见第 14 条),幂等可恢复。

14. **N=2 滚动重启任一 broker = 短暂 no-quorum 写阻塞**(**真机证实 2026-06-29**)。quorum=2 时重启一台 →
    剩 1/2 无 quorum → 那 ~5s 内**写全 fenced**(`not_leader`;读 + 存量 proxy 续)。我顺序重启 racknerd→pc732
    各一次,每次都有这个 blip。**改进/自动化**:滚动升级**先 `transfer-leader` 把 leadership 挪到不重启的那台
    再重启 + 聊天室通报**;或编排成只在 follower 上做。根上这是 **N=2(F=0)的固有脆弱**——文档应明确推荐
    生产 **N≥3**,N=2 仅过渡态。

15. **被 force-single 踢出的节点无法冷重启、又不能简单 rejoin(STUCK)**(**真机证实 2026-06-29 在线
    force-single**,扩展第 10/12 条)。force-single 后被弃节点(pc732)盘上 raft config 仍 `{pc732,racknerd}`
    (voters=2),冷启动撞 clustered-JS-quorum 陷阱(第 10 条)→ broker `error: cluster mode requires
    JetStream UNAVAILABLE (voters=2)` 退 70、systemd 重启 5 次后 failed;而幸存者已是 `{racknerd}`、不认
    pc732 → **pc732 既起不来又没法自己回去,卡死**。唯一出路 = 手动 wipe 过时 raft + `recovery rejoin
    prepare` + `cluster join approve`(多步)。**自动化/改进**:① 被弃节点冷启动检测"我已被 peer force-single
    踢出"(本地 config 含我、但 peer 集群不认)→ **actionable 报错直接指明 rejoin 步骤**,别崩溃循环 + 别尝试
    2-voter JS;② 一条 `tether cluster reabsorb <node>` 自动 wipe+rejoin 被弃节点回幸存集群(配对第 12 条:
    rejoin 成功后名册自然恢复正确)。

16. **【已纠正】部分集群可观测命令缺远程视图;但 `cluster status --remote` 本就存在(我没用)**(**真机证实
    2026-06-29**)。**先纠正本条初稿的误判**:`tether cluster status --remote` **本来就有**(`cluster.go:160`,
    经 NATS cluster-health 广播聚合、不需本机 socket),整场测试我却傻乎乎 SSH 上 broker 跑 `cluster status`。
    实测从笔记本:`cluster status --remote` 正确返回 `verdict: at least one broker reports emergency mode
    (force_single_active)…` —— **这就是从远端看 FORCE-SINGLE 的正确入口**(FORCE-SINGLE 不是 alert,`alert ls`
    看不到它,只能 status 看)。**仍存在的真缺口**:① `cluster status --homes` 和 `cluster seeds show` **没有**
    `--remote` 变体,仍只走本机 admin socket → 看 homing/seeds 仍得 SSH 上 broker;② `--remote` 是**简化 user
    summary**(只 1 行 verdict + "去 broker 跑全表"),不含 per-node 表/精确 voter 数;③ **`--remote` 在
    force_single 下 `exit=0`**(flag 文档说 exit 0/2/3,但实测 force_single 返回 0)→ 监控按 exit code 抓不到
    emergency,得解析 verdict 文本。**改进**:给 `--homes`/`seeds show` 加 `--remote`;`--remote` force_single

17. **【已纠正】cli-failover 本身是工作的;真缺口是 roster 动态发现被 floor 单点门住 + 运维要保持 ctl 二进制更新**
    (**真机证实 2026-06-29**;扩展第 9 条 = v0.4.6 已修)。**先纠正本条初稿的误判**:本次"pc732 死后本机 ctl 报
    `nats: no servers available`、没切 racknerd"的真因是——**当时跑的是旧 `v0.0.0-dev` 本机二进制,早于 v0.4.6、
    压根没 cli-failover**(= 用户当场判断正确),不是特性有缺陷。重建为当前源码后**实测**:把 broker_url 指向
    **已死的** `wss://weiland.top:443`,`tether node ls` **自动 failover 到 racknerd、成功返回全队**(走缓存
    `invite_seeds:[linziyang.top]` + `DialFor`)。所以 v0.4.6 cli-failover **能用**。**真正的(较小)代码缺口**:
    动态 roster 刷新 `refreshCtlEndpoints`(`cmd/tether/ctl_connect.go:70`)四重门——`PinAccountPub!="" &&
    FloorURL==base && BootstrapURL!="" && TTL过`——只在"连的正好是 `FloorURL` broker"且"`BootstrapURL` 可拉"
    (两者都钉**单台** broker=weiland.top)时才跑;故若只经 failover 连非-floor broker、或 floor/bootstrap broker
    已死(本例 pc732),缓存 `roster_gen` 永不更新(停在 setup 时的静态 invite_seeds)→ **学不到 setup 之后新增/变更
    的 broker**。failover 当下不受影响,但 roster 发现仍是 floor 单点的。**改进**:任一成功连接(不限 floor)都用该
    broker 在 §17/register 推送的**签名 roster**(见第 12 条)刷新缓存,使发现不依赖单一 floor/bootstrap host。
    **运维教训**:本机 ctl 二进制要跟着车队一起升级——这次就是它没升、误导了排查。

18. **proxy homing 在 broker 回归后不自动再均衡(failover 是"粘"的)**(**真机证实 2026-06-29**)。failover
    被动且粘:broker 一重启/死,它上面 home 的 proxy 全自动迁到当时唯一活着的 broker,**该 broker 重启回来后
    不迁回** → 分布越来越偏(本次仅 0.4.7 升级的两次 broker 重启,就把 5/6 个 proxy 挤到了 racknerd,且**全在
    杀 pc732 之前就迁好了**)。`cluster rebalance proxy` 是手动、且只动到均匀为止。**自动化**:broker rejoin/回归
    后 leader 自动评估并触发一次 proxy 再均衡(dry-run 可预览、受命脉稳定约束),别让分布永久倾斜。**注**:这条
    的"粘"+"复制态订阅"恰好是个**好性质**——broker 死时数据面不断、客户端从任一活 broker 抓到的 homing 一致;
    要自动化的只是"回归后再均衡",不是 failover 本身。

19. **同主机 broker/agent 版本可不一致,两个视图割裂**(**真机证实 2026-06-29**)。升级过程中 `node ls` 的
    RELEASE 列(agent 自报)与 `cluster status` 的 VER 列(broker 自报)在 pc732/racknerd 上一度不一致(broker
    已 0.4.5/0.4.7、agent 还 0.4.3),因为 broker 守护与同机 agent 是**两个进程、分别重启、时机不同**。容易误判
    "升完了"其实只升了一半进程。**改进**:`node ls -a` 对 broker 主机同时显示 broker+agent 两个版本(或对同机
    skew 标 warning),让"整机升级"有单一可信判据。

20. **force-single 后幸存者的 nats.conf 滞留 clustered → JetStream 静默 503 腐烂(可数天无人察觉),且幽灵
    VOTER 挡死全部在线去集群化路径**(**真机证实 2026-07-04**:racknerd 单 broker,pc732 已物理退役被
    racknerd 取代)。**这是第 10/12 条在"survivor 侧"的合流,且比崩溃循环更隐蔽——不再退 70,而是活着烂**。
    **机理**:N=2 时 racknerd 的 `nats.conf` 有 `cluster{}` 块、route 指向 pc732(`nats://155.98.36.32:6222`)。
    杀 pc732 后 **online force-single 只热换 raft 成 {racknerd}**、**完全不碰 nats.conf**;于是独立的
    `nats-server.service` 仍以 **clustered JetStream** 跑,JS meta-group 成员是 {racknerd,pc732}、pc732 永不回来
    → **1/2 无 quorum → 每个 JS API 调用返 `503 err_code=10008 "JetStream system temporarily unavailable"`**。
    v0.4.7 的 broker **不再退 70 崩溃循环(第 10 条早期行为),而是活着每 ~0.5s 刷一条 WARN 重试**(`d5: replica
    reconcile create events`、`d8b: list streams`、`audit publish`)——**本次现网就这么烂了 5 天(6-29 04:21 →
    7-04)无人察觉**:控制面(node ls/exec/expose 端口分配/隧道)全走 tether 自己的 raft(N=1)+ core NATS、不碰
    JS,所以表面一切正常,只有 **JetStream 依赖面全废**:push/pull 全层(**连 tier-A 小文件也废——pull 路径先
    `create_bucket` 建 JS Object Store**,报 `bucket_create_failed ... 503`)、history/深度 ps、audit 发布。
    **修 = 让 survivor 的 nats.conf 降回 standalone JetStream**(`reconcile nats --to-standalone --confirm-single`
    重渲染去掉 cluster{} 块 + **完整重启 nats-server**,重启会断经 broker 的 ctl 通道→必须 detached/`systemd-run`)。
    standalone N=1 的 JS quorum 平凡满足、流恢复。**⛔ 但本次 `--to-standalone` 被幽灵 pc732 挡死**:报
    `node "pc732" has an unrecognized raft role "" — cannot prove N=1, refusing`——它扫 roster 表,pc732 的 raft
    role 空(force-single 早把它移出 raft config、但第 12 条留着它 phase=VOTER 的行)→ 无法证明 N=1 → 拒。而想清
    幽灵解锁:`recovery node remove pc732 --manual` 拒(`node is VOTER; raw remove only finishes RETIRING/
    VOTER_ADD_FAILED/CATCHING_UP`)、`cluster retire pc732` 拒(`cannot retire the last voter`)——**第 12 条的
    "三不沾" deadlock 在 0.4.7 依旧,在线无任何工具删除路径**(pc732 已死、rejoin 不可能)。**本次绕过办法(手动、
    非工具)**:直接 awk 剥掉 nats.conf 顶格 `cluster{}` 块(pc732 确死、无 live route peer 可撕,de-cluster 安全)
    → `nats-server -t` 校验 → `.bak` 备份 → 停 nats + `mv jetstream jetstream.clustered-bak.<ts>`(reset 旧
    clustered store,standalone 不迁 clustered 流,同第 4/3a 条,mv 可回滚) → 起 nats。**注意持久性**:broker **不在
    启动时重渲染 nats.conf**(实证 nats.conf mtime 5 天没变、broker 期间重启多次未动它),故手改的 standalone conf
    **跨 broker 重启存活**;唯一会翻回 clustered 的触发是**成员/topology-gen 前进的操作**(join/retire/`reconcile
    nats`)——而幽灵删不掉、我也不做这些,所以稳。**该怎么自动化/修**:① **force-single 必须同时把 survivor 的
    nats.conf 降回 standalone**(不能只换 raft 留 NATS 挂着烂),受 R3"不静默 de-cluster"约束需谨慎但这是 survivor 自
    救、非成员操作;② 修第 12 条(force-single 把被弃节点 roster phase 降级为非-VOTER,或 `recovery node remove`
    对"不在 raft config 的幽灵"跳过 RemoveServer 直接删 roster 行)——一旦幽灵可删,`--to-standalone` 自然解锁,
    整条链回到工具路径;③ **JS 503 持续应触发告警**(现在 `alert ls` 只有 `[info] broker_down`,force_single 靠
    ctl 合成、JS-down 干脆无告警),数天 JS 全废却无任何主动信号是最大的运维盲区。

21. **broker 硬编码 8 GiB OBJ_xfer 预留,小盘 broker 上 tier-B 传输被 JS storage 准入拒(`10047 insufficient
    storage resources`)**(**真机证实 2026-07-04**,承第 20 条修好 JS 503 之后暴露)。`ensureXferBucket`

22. **install.sh 漏 chown `/etc/tether` → in-broker nats.conf reconciler 以 tether 跑却写不了 → membership
    变更后 topology 永不自动收敛(卡 DEGRADED)**(**模拟集群证实 2026-07-05**)。**机理**:install.sh
    (`scripts/install.sh:491-492`)用 `install -d -o tether -g tether` 把 `/var/lib/tether`(LIB_DIR)/log/run
    交给 tether,**唯独 `/etc/tether`(ETC_DIR)留给 root**(root 建、无 chown)。而 in-broker C3 topology
    reconciler 以 `User=tether` 跑,grow/retire 后要**原子重写 nats.conf**——`internal/natsconf/takeover.go:190`
    `os.CreateTemp(dir, ".nats.conf.*")`,dir=`/etc/tether` → **`permission denied`** → topology 停在旧
    generation → `cluster status` 报 DEGRADED(`a broker's NATS topology has not caught the desired
    generation yet`),**即使 raft/JS/routes 全 HA**(实测 N=3 三 VOTER + stream R=3 全副本 + 3-node JS meta,
    唯一卡点就是这个 perm-denied)。**真机被掩盖的原因**:运维手动 `sudo tether cluster reconcile nats --all`
    是以 root 跑、能写,于是每次成员变更都靠人工 root reconcile 兜底,没人注意到 in-broker 自动 reconciler 一直
    在静默失败。**该怎么修**:install.sh 给 ETC_DIR 也 `install -d -o tether`(或至少让 nats.conf 所在目录
    tether 可写),让 in-broker reconciler 能自动收敛,membership 变更后不必人工 root reconcile。
    > **更正(2026-07-05)**:#22 是真产品缺陷(install.sh 不 chown ETC)。模拟集群**天然复现**它——全新 docker
    > named volume 挂载点是 **root:root**、install.sh 只 chown LIB/LOG/RUN 不碰 ETC,故 /etc/tether 天然 root-owned,
    > 无需 sim 任何 chown。但曾有一段时间被一个**陈旧 baked 镜像**掩盖:早期 provision 版本 DID chown ETC→tether
    > (M6 删了该 chown 但 4 小时前的镜像没重建、baked 的是旧版),那阵子 /etc/tether 是 tether-owned、in-broker
    > reconciler 能写、#22 没发生(当时的 DEGRADED 其实是 config_load_time/SIGHUP 误判;`doctor` tripwire 一直在
    > warn 无人留意)。重建镜像后 /etc/tether 恢复 root-owned。**复现方式**(drill `13-inbroker-reconcile-perm`):以
    > tether 跑 `reconcile nats --manual --skip-dry-run` 写 root-owned /etc/tether → `natsconf: temp/write .bak:
    > … permission denied`(in-broker reconciler共享的同一 natsconf.Apply 写路径;真 reconciler 被 grow 的 root 前
    > 渲染 front-run,不亲自触发)。`provision-node.sh` **刻意不 force owner**,故 install.sh 修好(chown ETC→tether)
    > 后 drill 13 会 flip GREEN。教训:容器化 harness 的**镜像/baked 层陈旧**会悄悄掩盖 install-path 缺陷,`doctor`
    > owner tripwire + 重建后校验是防线。

23. **tether-broker 丢 nats 连接后 clean-exit(0) + 单元 `Restart=on-failure` → 任何 nats-server 重启/较长
    中断后 broker 永久不回来**(**模拟集群证实 2026-07-05**)。**机理**:nats-server 重启时运行中的 tether-broker
    丢连接后**干净退出**(日志 `broker: shutting down`、exit 0),而 install.sh 写的 `tether-broker.service` 是
    `Restart=on-failure` → **clean exit 不触发重启** → broker 停死(systemd 显示 inactive 而非 failed),要人工
    `systemctl start`。**影响面**:grow runbook 里的 `systemctl restart nats-server` 步骤、nats crash/OOM 自
    恢复、force-single 后的 nats 重启——只要 broker 当时在跑就会被弄死,而运维往往只重启 nats、以为 broker 会
    自愈。**该怎么修(内审 m8 校正:broker 已设 `nats.MaxReconnects(-1)`(`internal/broker/authcallout.go:36`)
    永久重连,故"无限重连"是部分 no-op;真正干净退出的是某条 loop/subscription 在 nats 掉线时主动 return,该调用点
    未定位。durable 修复几乎肯定在单元层——`install.sh:734` 的 `Restart=on-failure` 改 `Restart=always`。驱动产品
    改动前先抓 survivor 干净退出那刻的 journal + 定位 return 点)**:broker 在 nats 断连时应**无限重连**(不主动退出),或退出用**非 0** 码让
    `Restart=on-failure` 接住,或单元改 `Restart=always`。(模拟集群实测:第二次 grow 若 `restart` 已入群 voter
    的 nats,会把已是 VOTER 的 broker 弄死、退回 CATCHING_UP;改用 `SIGHUP reload` 而非 restart 规避。)

24. **`route-cert.pem` 必须带 SAN 才能形成 nats-server route mesh,但 tether 无证书工具 + 无文档 + raft
    transport 的注释反向误导**(**模拟集群证实 2026-07-05**)。**机理**:同一张 `route-cert.pem` 被两处 TLS 用——
    (a) tether **自己的 raft transport**:`internal/cluster/transport.go:91` 明设 `InsecureSkipVerify:true`
    **只跳 hostname**(注释:"raft addrs 无 SAN"),CN-only 证书 OK;(b) **nats-server 的 cluster route mesh**:
    渲进 nats.conf 的 `cluster{tls{verify:true}}` 做**标准 Go x509 校验**,Go 1.15+ **要求 SAN**,CN-only 证书被拒
    `x509: certificate relies on legacy Common Name field, use SANs instead` → route 握手关闭 → **routes 形不成
    → clustered JS meta 形不成 → 新 voter 卡 CATCHING_UP**。tether **本身不生成证书**(`clusteroffline/preflight.go`
    只校验存在),操作者/自动化自行 openssl 铸;若照 transport.go 的"无 SAN"直觉铸成 CN-only,raft 能起但 nats
    route mesh 全废。**该怎么修**:文档明确 route/tunnel leaf **必须带 `subjectAltName=DNS:<server_name>`**
    (与 raft transport 的无-SAN 假设相反);或 tether 提供证书铸造(现在 `cluster keygen` 只铸 nkey)自动带 SAN。
    (模拟集群实测:CN-only ed25519 route 证书 → `num_routes=0`、JS meta 不成、grow 卡住;加 `DNS:<node>` SAN 后
    routes 通、meta 成、grow 成 VOTER。)

## B. 终极自动化目标
把整条 grow 序列（leader resnapshot 若需 → joiner init → join → 渲染 mesh → reset JS → 发布 seed →
rebalance proxy）收进**一条 `tether cluster add <new-broker>` 编排命令 / 向导**，全自动幂等可恢复，
而不是本次的 ~15 步手动 + detached 脚本 + pty 喂 confirm + 多次重试。

> **进展(2026-07-05)**:`test/simcluster/simcluster grow <joiner>` 已把这条序列**跨进程跑通并稳定
> 复现(N=1→2→3、全 VOTER)**,可作为 `tether cluster add` 编排的**可执行规格**。已实证钉死的关键顺序:
> ① `join approve` **不带 `--wait`**(joiner 未 catch up 前 --wait 会死等,曾卡 20 分钟);② 先把**所有
> broker 渲成 clustered + 互为 route peer**(全 mesh)、former-N1 首次 reset JS(#4)、再启动 joiner——否则
> 撞 N=1-clustered-JS 陷阱(#10);③ 给已入群 voter 加 route 用 **SIGHUP reload**、别 restart(#23);
> ④ route 证书带 **SAN**(#24);⑤ reconciler 的 nats.conf 可被 `User=tether` 写(#22)。这些正是 §A 里 #3/#4/#8/#10 的自动化落地。
> **更正(G1 已修,2026-07-05)**:#22 采纳 **Option B** ——把 reconciler 的 nats.conf 迁进 tether-owned 的 `/etc/tether/nats.d/` 子目录,`/etc/tether` **本身保持 root-owned**(root 跑的 caddy 读 `/etc/tether/Caddyfile`,若 chown 整个 `/etc/tether` 会成 tether→root 本地提权)。故上面 ⑤ 的旧设想"chown 整个 `/etc/tether` 让 tether 可写"**已被否决**;正确形态是 `/etc/tether` root-owned + `/etc/tether/nats.d/` tether-owned。#23 unit `Restart=always`、#24 route/tunnel leaf 须带 SAN 匹配 route-URL host,均见 `docs/reviews/g1-plan.md`。
